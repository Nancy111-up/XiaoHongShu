# 体育品牌运营 Agent 真实工作闭环设计

## 目标

把当前“能打开但没有内容”的工作台补成可实际操作的数据闭环。系统坚持真实数据原则：不使用伪造机会填充页面；无数据时明确说明原因、当前阶段和下一步操作。

## 根因

当前 `POST /api/refresh-jobs` 只在数据库创建 `queued` 记录，没有执行器消费任务。前端在创建任务后立即重新读取机会，因此数据库仍为空。内容工作室、内容日历和数据复盘虽然已有读取端点，但没有上游内容写入，自然也为空。

## 架构与数据流

一次刷新采用应用内后台任务执行，不另引入消息队列：

1. API 创建刷新任务并立即返回任务 ID。
2. 后台运行固定版本 MediaCrawler，按品牌关键词执行搜索与详情两阶段采集。
3. 标准化笔记和评论，聚类主题，生成证据快照。
4. 调用统一 AI 服务完成维度评分、解释与文案预览；缺少 AI 配置时保留采集结果，并把任务标记为可解释的部分完成。
5. 保存机会及其证据引用，任务进入 `completed`、`partial_success` 或 `failed`。
6. 前端轮询任务状态，显示当前阶段和失败原因；结束后重新读取机会列表。
7. 用户接受机会后生成草稿；草稿可进入日历；复盘页读取数据库聚合结果。

同一时间只允许一个刷新任务。应用重启时，超过期限的活动任务按既有恢复规则处理，避免永久卡在“进行中”。

## 后端组件

- `RefreshRunner`：组合配置、MediaCrawler 适配器、两阶段协调器、主题解析和机会分析服务。
- 刷新 API：在成功创建任务后启动后台执行，并返回可轮询的任务 ID。
- 状态 API：除状态外返回阶段、成功/失败关键词、错误摘要和更新时间。
- 机会生成：只从真实采集证据创建机会，并保存来源关联。
- 内容与日历：接受机会生成草稿；草稿排期继续使用现有数据库模型和接口。
- 降级策略：采集失败不制造数据；单个关键词或详情采集失败允许部分成功；AI 未配置时明确提示配置项。

## 前端体验

- 刷新按钮启动真实任务，随后显示采集、整理、分析等进度，任务进行中禁止重复点击。
- 空状态展示三类信息：为什么为空、系统当前状态、用户可以执行的动作。
- 热点机会展示真实列表、评分、证据来源和接受/拒绝操作。
- 内容工作室、日历、复盘和品牌大脑保持统一白底森林绿外壳，并展示真实记录、加载状态、错误状态和有效操作。
- 顶部数据源标记区分真实、部分可用和不可用，不将测试或演示数据标为真实。

## 接口约定

- `POST /api/refresh-jobs` 返回 `{ id, status }`。
- `GET /api/refresh-jobs/{id}` 返回任务状态、阶段详情、错误摘要和更新时间。
- `GET /api/opportunities` 在刷新完成后返回真实机会及 `data_source`。
- 现有品牌、草稿、日历和复盘接口保持兼容；仅在缺少工作流所需字段时做向后兼容扩展。

## 错误与安全

- 日志和 API 响应不得暴露 Cookie、令牌或完整浏览器凭据。
- MediaCrawler 登录失效时提示“需要重新登录采集账号”，不返回底层敏感输出。
- 前端网络中断后可继续轮询或手动重试，不重复创建任务。
- 原始采集数据写入项目数据目录，不纳入 Git。

## 测试与验收

- 单元测试覆盖任务启动、并发刷新、状态变化、失败脱敏和机会生成。
- 集成测试覆盖“创建任务 → 执行协调器 → 机会入库 → 前端可读取”。
- 前端测试覆盖轮询、阶段提示、失败提示、刷新完成后加载机会，以及五个模块的非空真实状态。
- 运行后端全量测试、前端测试、代码检查和生产构建。
- 浏览器人工验收刷新进度、模块切换、接受机会、保存品牌资料和空/错状态。

## 范围边界

本轮不加入伪造演示数据、不引入独立队列服务、不自动发布到社交平台，也不绕过小红书登录与平台限制。重点是打通本地单用户 V0.1 的真实采集、分析、内容生产和查看闭环。
